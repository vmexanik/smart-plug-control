# Smart Plug Control (ESP32-WROOM, ESP-IDF)

ESP32-хаб для керування розумними розетками по **HTTP** та **MQTT** (Tuya/Xiaomi свідомо не підтримуються). Веб-морда для CRUD розеток, кнопка тестового вкл/викл, журнал подій з ротацією, 3 GPIO-входи (AC1/DC1/DC2) як тригери, системні налаштування з множинним вибором активних входів. Драйвер Zigbee закладений як заглушка на майбутнє.

Написано й перевірено проти **ESP-IDF v6.0.1** (у пісочниці немає xtensa-toolchain, тож збірку робив користувач локально — знайдені по ходу проблеми з `REQUIRES` вже виправлені, див. нижче).

## Структура проєкту

```
CMakeLists.txt
partitions.csv          # nvs + phy_init + factory app (1.5MB) + "storage" LittleFS (384KB)
sdkconfig.defaults
main/
  Kconfig.projbuild      # дефолтні GPIO для AC1/DC1/DC2, AP fallback SSID/пароль, HTTP порт
  app_main.c              # ініціалізація та порядок запуску
  app_types.h             # спільні структури (plug_t, system_settings_t, ...)
  storage.c/h             # LittleFS: config.json (розетки + налаштування)
  event_log.c/h           # ND-JSON журнал подій з ротацією файлів
  gpio_inputs.c/h         # опитування 3 входів з debounce
  plug_manager.c/h        # CRUD розеток, диспетчер драйверів, реакція на входи
  driver_http.c/h         # HTTP драйвер (GET/POST on_url/off_url, basic auth)
  driver_mqtt.c/h         # спільний MQTT-клієнт, публікація команд
  driver_zigbee.c/h       # заглушка (ESP_ERR_NOT_SUPPORTED) — точка розширення
  wifi_manager.c/h        # STA (з NVS) + постійний fallback AP на 192.168.4.1
  web_server.c/h          # REST API + віддача вбудованої веб-морди
  cJSON.c/h                # вендорений мінімальний JSON-парсер/принтер (див. нижче, чому)
  web/index.html, app.js, style.css   # односторінковий UI, вбудовується у прошивку (EMBED_FILES)
```

## Збірка та прошивка

```bash
idf.py set-target esp32
idf.py build
idf.py -p <PORT> flash monitor
```

Компоненти `joltwallet/littlefs` та `espressif/mqtt` підтягнуться автоматично через `main/idf_component.yml` (component manager) при першому білді.

**Чому не стандартні `mqtt`/`json` компоненти ESP-IDF.** У ESP-IDF v6.0.1 обидва компоненти прибрані з ядра (перевірено діфом `.gitmodules` між версіями — submodule cJSON зник, а `components/mqtt` лишився порожньою заглушкою):
- `esp-mqtt` тепер підключається як керований компонент `espressif/mqtt` (додано в `idf_component.yml`, `REQUIRES` вказує на `espressif__mqtt` — саме таке ім'я отримує тека `managed_components/espressif__mqtt`).
- cJSON вендорено напряму в `main/cJSON.c/h` — мінімальна власна реалізація, що покриває рівно ті функції cJSON API, які реально використовуються в проєкті (`cJSON_Parse`, `cJSON_PrintUnformatted`, `cJSON_Add*ToObject`, `cJSON_Is*`, `cJSON_ArrayForEach` тощо). Це прибирає залежність від того, під яким іменем (якщо взагалі) Espressif надалі публікуватиме cJSON у реєстрі компонентів.

`esp_driver_gpio` (замість застарілого `driver`) звірено напряму проти тегу `v6.0.1` в репозиторії esp-idf — актуальна назва.

> Якщо `idf.py build` все ж лається на `REQUIRES component "X" not found` — залишок цього списку (`nvs_flash`, `esp_wifi`, `esp_netif`, `esp_event`, `esp_http_server`, `esp_http_client`, `esp_timer`) вже підтверджений реальним логом збірки користувача (впав лише на `mqtt`, решта резолвилась без помилок).

## Підключення входів

3 фіксовані логічні входи: **AC1, DC1, DC2**. Дефолтні GPIO задаються в `menuconfig → Smart Plug Control → Default trigger input GPIOs` (за замовчуванням 34/35/32 — вхідні пінами без підтяжки, підходять для опто-розв'язаних сигналів). GPIO-номер кожного входу та те, чи він активний, можна також змінити пізніше без перепришивки — в системних налаштуваннях веб-морди.

Логіка: **1 на вході → прив'язана розетка увімкнена, 0 → вимкнена**. Прапорець "інверсія" на кожній розетці інвертує це правило індивідуально (одна розетка на вході може бути "нормально відкритою", інша "нормально закритою"). Розетка може бути не прив'язана до жодного входу (`input = NONE`) — тоді керується лише вручну/через API.

## Веб-морда

`http://<ip-пристрою>/` — вкладки:

- **Розетки** — список, додавання/редагування/видалення, кнопки ON/OFF для ручної перевірки, індикатор останнього стану.
- **Системні налаштування** — які входи слухати (мультивибір) + їх GPIO, debounce/період опитування, спільний MQTT-брокер, параметри ротації журналу.
- **Wi-Fi** — SSID/пароль STA-мережі; резервна AP завжди активна.
- **Журнал подій** — останні N записів (джерело: input/manual/api/boot/system), очищення.

## REST API (для довідки / інтеграцій)

| Метод | Шлях | Опис |
|---|---|---|
| GET | `/api/plugs` | список розеток |
| POST | `/api/plugs` | створити розетку |
| PUT | `/api/plugs/{id}` | оновити розетку |
| DELETE | `/api/plugs/{id}` | видалити розетку |
| POST | `/api/plugs/{id}/action` | `{"action":"on"|"off"}` — ручна перевірка |
| GET/POST | `/api/settings` | системні налаштування |
| GET | `/api/log?limit=N` | останні N подій (ND-JSON масив) |
| POST | `/api/log/clear` | очистити журнал |
| GET | `/api/status` | стан входів, Wi-Fi, uptime |
| GET/POST | `/api/wifi` | STA SSID/пароль |

## Wi-Fi

Пристрій завжди піднімає AP `SmartPlug-XXXXXX` (пароль з Kconfig, за замовчуванням `plugsetup`) на `192.168.4.1` — це гарантує доступ до веб-морди навіть якщо STA не налаштована/недоступна. STA-креденшали зберігаються в NVS і застосовуються без перепришивки через вкладку Wi-Fi.

## Драйвери

- **HTTP** — окремі `on_url`/`off_url` (GET або POST), опційний Basic Auth, опційний `status_url` (зарезервований, наразі не опитується автоматично).
- **MQTT** — один спільний клієнт на весь пристрій (адреса брокера в системних налаштуваннях); кожна розетка має свій `cmd_topic` + `payload_on/off`, QoS, retain.
- **Zigbee** — `driver_zigbee.c` є заглушкою: команди повертають `ESP_ERR_NOT_SUPPORTED` і пишуться в журнал як помилка. Причина: звичайний ESP32-WROOM не має радіо 802.15.4. Коли з'явиться супутній Zigbee-координатор (наприклад ESP32-H2/C6 по UART, або esp-zigbee-sdk), реалізацію можна додати всередину `driver_zigbee_set()` — схема конфігурації розетки (`plug_t.zigbee`), сховище, веб-морда (пункт "Zigbee" вже є в селекторі драйвера) і диспетчер у `plug_manager.c` міняти не потрібно.

## Відомі спрощення / що варто допрацювати

- Часові мітки в журналі — секунди від старту пристрою (uptime), а не абсолютний час: NTP не підключений. За потреби додати `esp_sntp` і писати `time(NULL)`.
- `status_url` в HTTP-драйвері поки не використовується для читання фактичного стану розетки (лише зберігається в конфігурації) — легко додати опитування статусу за потреби.
- Немає TLS/mTLS для HTTP чи MQTT (свідомо, за умовою задачі — лише прості HTTP/MQTT драйвери); за потреби `esp_http_client`/`esp-mqtt` підтримують `https://`/`mqtts://` без зміни архітектури.
- Вендорений `cJSON.c/h` — це не офіційна бібліотека DaveGamble/cJSON, а власна мінімальна реалізація з такою ж назвою функцій. Парсер толерантний до "сирого" JSON, який генерує сам пристрій, але не проходив повний conformance-тест (наприклад, юнікод-сурогатні пари `\uD8xx\uDCxx` не збираються в один кодпоінт — для ASCII-даних цього проєкту це не критично).
