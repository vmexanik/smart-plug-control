# Smart Plug Control (ESP32-S3-WROOM-1, ESP-IDF)

ESP32-S3-хаб для керування розумними розетками по **HTTP** та **MQTT** (Tuya/Xiaomi свідомо не підтримуються). Веб-морда для CRUD розеток, кнопка тестового вкл/викл, журнал подій з ротацією, 3 GPIO-входи (AC1/DC1/DC2) як тригери, системні налаштування з множинним вибором активних входів. Драйвер Zigbee закладений як заглушка на майбутнє.

Написано й перевірено проти **ESP-IDF v6.0.1** (у пісочниці немає xtensa-toolchain, тож збірку робив користувач локально — знайдені по ходу проблеми з `REQUIRES` вже виправлені, див. нижче).

**Апаратна платформа: ESP32-S3-WROOM-1-N16R8** (16MB флеш, 8MB Octal PSRAM). Проєкт починався на класичному ESP32-WROOM-32 і був перенесений на S3 — головні наслідки переносу: інші дефолтні GPIO для входів (`Kconfig.projbuild`, класичні 34/35/32 фізично зайняті під флеш/PSRAM на цьому модулі), окремий `sdkconfig.defaults.esp32s3` з увімкненим PSRAM (`CONFIG_SPIRAM=y`), і значно менше памʼяті-орієнтованих обмежень — `malloc()` понад 16KB (`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`) тепер прозоро йде в PSRAM, тож фрагментація/вичерпання внутрішньої SRAM, що раніше змушувала уважно проєктувати API (`net_scan_get_result()` по одному елементу замість одного великого масиву — див. коментар у `net_scan.h`), тепер значно менш імовірна. Радіо 802.15.4 (Zigbee/Thread) на S3, як і на класичному ESP32, немає — це лише в C6/H2.

**Відомий підводний камінь переносу:** розміри стеків задач, підібрані й перевірені на класичному ESP32 (Xtensa LX6), виявились замалими на S3 (Xtensa LX7) для задач, що викликають `esp_http_client` -- перший же реальний виклик (натискання on/off у веб-морді) провалював стек глибше за canary-зону перевірки переповнення, і замість зрозумілого повідомлення про це система падала з незрозумілою `Guru Meditation (LoadProhibited)` **всередині самого FreeRTOS-планувальника** (`prvSelectHighestPriorityTaskSMP`) з "отруєними" регістрами `0xa5a5a5a5` -- класичний відкладений симптом переповнення стека, що зачепило чужу структуру в памʼяті, а не сам винуватець. Стеки `plug_manager.c`'s `worker_task`, HTTP-сервера (`web_server.c`) і `net_scan.c`'s `net_scan_task` підняті з 8192 до 12288 байт; додатково увімкнено `CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK` (апаратний watchpoint, ловить запис в останні 32 байти стека будь-якої задачі точно в момент переповнення) — якщо колись знову не вистачить стека, буде чіткий панік з точним місцем, а не ця головоломка.

## Збірка та прошивка

```bash
idf.py set-target esp32s3
idf.py build
idf.py -p <PORT> flash monitor
```

Якщо проєкт раніше вже збирався під `esp32` (класичний WROOM-32) в цій самій теці, `set-target` сам перегенерує `sdkconfig` під новий чіп -- але про всяк випадок, якщо після цього щось не так (лишились старі значення), надійніше видалити його вручну і зібрати наново:

```bash
rm sdkconfig   # на Windows: del sdkconfig
idf.py set-target esp32s3
idf.py build
```

Компоненти `joltwallet/littlefs` та `espressif/mqtt` підтягнуться автоматично через `main/idf_component.yml` (component manager) при першому білді.

**Чому не стандартні `mqtt`/`json` компоненти ESP-IDF.** У ESP-IDF v6.0.1 обидва компоненти прибрані з ядра (перевірено діфом `.gitmodules` між версіями — submodule cJSON зник, а `components/mqtt` лишився порожньою заглушкою):
- `esp-mqtt` тепер підключається як керований компонент `espressif/mqtt` (додано в `idf_component.yml`, `REQUIRES` вказує на `espressif__mqtt` — саме таке ім'я отримує тека `managed_components/espressif__mqtt`).
- cJSON вендорено напряму в `main/cJSON.c/h` — мінімальна власна реалізація, що покриває рівно ті функції cJSON API, які реально використовуються в проєкті (`cJSON_Parse`, `cJSON_PrintUnformatted`, `cJSON_Add*ToObject`, `cJSON_Is*`, `cJSON_ArrayForEach` тощо). Це прибирає залежність від того, під яким іменем (якщо взагалі) Espressif надалі публікуватиме cJSON у реєстрі компонентів.

`esp_driver_gpio` (замість застарілого `driver`) звірено напряму проти тегу `v6.0.1` в репозиторії esp-idf — актуальна назва.

> Якщо `idf.py build` все ж лається на `REQUIRES component "X" not found` — залишок цього списку (`nvs_flash`, `esp_wifi`, `esp_netif`, `esp_event`, `esp_http_server`, `esp_http_client`, `esp_timer`) вже підтверджений реальним логом збірки користувача (впав лише на `mqtt`, решта резолвилась без помилок).

## Підключення входів

3 фіксовані логічні входи: **AC1, DC1, DC2**. GPIO-номери **не редагуються з веб-морди** — це свідоме рішення: вони прошиті через `menuconfig → Smart Plug Control → Default trigger input GPIOs` (за замовчуванням 34/35/32 — вхідні піни без підтяжки, підходять для опто-розв'язаних сигналів) і застосовуються через `storage_force_fixed_inputs()` (`main/storage.c`), яка перезаписує GPIO-поля кожного разу при завантаженні конфігу і при кожному збереженні системних налаштувань — навіть якщо в `config.json` чи в запиті до `/api/settings` прийде інше значення, воно ігнорується. Щоб змінити піни, треба перепрошити пристрій з новим `menuconfig`. З веб-морди редагується лише **чи слухати** кожен вхід (enable/disable), множинний вибір.

Логіка: **1 на вході → прив'язана розетка увімкнена, 0 → вимкнена**. Прапорець "інверсія" на кожній розетці інвертує це правило індивідуально (одна розетка на вході може бути "нормально відкритою", інша "нормально закритою"). Розетка може бути не прив'язана до жодного входу (`input = NONE`) — тоді керується лише вручну/через API.

## Веб-морда

`http://<ip-пристрою>/` — вкладки:

- **Розетки** — список, додавання/редагування/видалення, кругла іконка-кнопка живлення для ручного on/off (зелена/червона за поточним станом), індикатор останнього стану, потужність/напруга/струм під назвою для розеток з енергомонітором (див. розділ "Моніторинг споживання"), кнопка "Знайти в мережі" (див. розділ "Автопошук у мережі").
- **Системні налаштування** — які входи слухати (мультивибір; GPIO-піни, debounce і період опитування фіксовані прошивкою, тут лише для довідки), Wi-Fi (SSID/пароль STA), спільний MQTT-брокер, дата і час (лише ручне встановлення — NTP-сервер задається в прошивці), параметри ротації журналу.
- **Журнал подій** — останні N записів (джерело: input/manual/api/boot/system), очищення.

|---|---|---|
| GET | `/api/plugs` | список розеток (кожен об'єкт також містить `metrics: {valid, power_w, voltage_v, current_a, updated_us}` — див. розділ "Моніторинг споживання") |

## Wi-Fi

Пристрій завжди піднімає AP `SmartPlug-XXXXXX` (пароль з Kconfig, за замовчуванням `plugsetup`) на `192.168.4.1` — це гарантує доступ до веб-морди навіть якщо STA не налаштована/недоступна. STA-креденшали зберігаються в NVS і застосовуються без перепришивки через вкладку "Системні налаштування" (розділ Wi-Fi).

Поле пароля на вкладці налаштувань підвантажує поточний збережений пароль (кнопка "Показати"/"Сховати" перемикає видимість) — раніше поле завжди було порожнім, тож натискання "Підключити" без повторного вводу пароля відправляло порожній рядок і затирало робочі креденшали. Веб-морда цього пристрою не має власної автентифікації (будь-хто в тій самій мережі й так може змінити налаштування), тож повернення пароля назад у відповіді `GET /api/wifi` не є новою діркою в безпеці.

Кнопка "Знайти мережі" запускає `esp_wifi_scan_start()` (блокуючий виклик у власній задачі — `wifi_scan_task` в `wifi_manager.c`) і показує знайдені мережі списком (клік по рядку — як і у пошуку розеток, без окремої кнопки-дії): SSID, орієнтовний рівень сигналу з RSSI (4 поділки), позначка "відкрита" для мереж без пароля. Мережі з однаковим SSID (типово — mesh/декілька точок доступу) дедуплікуються: лишається запис з найсильнішим сигналом, бо `esp_wifi_scan_get_ap_records()` вже повертає список відсортованим за RSSI. Приховані мережі (порожній SSID) не показуються — такий SSID можна ввести вручну, поле не заблоковане тільки для вибору зі списку. Сканування триває секунди й, за документацією Espressif, не розриває вже активне STA-з'єднання (типовий час на канал ~120мс, значно менше порогу ~1500мс, після якого можливий розрив).

Якщо STA-з'єднання рветься з причиною, яку повторні спроби самі не виправлять (невірний пароль -- `WIFI_REASON_AUTH_FAIL`, SSID не знайдено -- `WIFI_REASON_NO_AP_FOUND`, і кілька суміжних кодів; повний список — `is_config_error_reason()` у `wifi_manager.c`), `wifi_manager` рахує такі підряд і після 3 невдалих спроб припиняє автоперепідключення (`config_error` в `/api/status`/`/api/wifi` стає `true`, веб-морда показує попередження). Звичайні тимчасові розриви (роутер перезавантажився, Wi-Fi "моргнула") під цей лічильник не підпадають і ретраяться, як і раніше, без обмежень. Лічильник скидається при успішному підключенні або новій спробі зберегти креденшали з форми.

## Дата і час

ESP32 без RTC-батареї стартує з часом 1970-01-01 (epoch 0). `time_sync.c` (обгортка над `esp_netif_sntp`) неблокуюче "заряджає" NTP-клієнт при старті проти сервера з `CONFIG_NTP_SERVER_DEFAULT` (`menuconfig → Smart Plug Control → NTP server`, за замовчуванням `pool.ntp.org`) — **сервер не редагується з веб-морди**, лише перепрошивкою з новим `menuconfig`, за тим самим принципом, що й GPIO-піни входів. Фактична синхронізація відбувається, щойно STA отримає IP і зможе достукатись до сервера. Якщо інтернету немає (лише AP-режим) або `CONFIG_NTP_SERVER_DEFAULT` порожній — час можна виставити вручну через вкладку "Системні налаштування" (поле "Встановити вручну" → `POST /api/time`, це окрема, незалежна від NTP дія). Журнал подій (`event_log.c`) пише `time(NULL)` — тобто мітки будуть коректними лише після синхронізації одним із цих двох способів; до того — це відлік від 1970 року, але видно статус (`synced`/`source` через `GET /api/time`) і є спосіб це виправити без очікування.

## Драйвери

- **HTTP** — окремі `on_url`/`off_url` (GET або POST), опційний Basic Auth, опційний `status_url` (зарезервований, наразі не опитується автоматично). У формі розетки поле "Драйвер / протокол" тепер, крім HTTP/MQTT/Zigbee, напряму пропонує **Shelly (Gen1)**, **Shelly (Gen2+/Gen3)** і **Tasmota** окремими пунктами (усі три технічно все ще виконуються через `driver_http.c` — це `driver=http` з заданим `http.family`, окремого виконавчого коду на кожну прошивку немає й не планується, див. пункт нижче в "Свідомо не перенесено"). Вибір такого пункту ховає поля URL і замінює їх на єдине поле "IP або хост пристрою" — адреси `on_url`/`off_url` генеруються на льоту в браузері за тим самим шаблоном, що й `fingerprint.c` при скані (`app.js: FAMILY_URL_TEMPLATES`). Якщо розетку додано через "Знайти в мережі" і протокол розпізнано автоматично — той самий пункт вибирається сам, поле хоста підставляється з IP знахідки. Для нерозпізнаних пристроїв (ручне додавання, ESPHome) URL лишаються звичайними текстовими полями.
  При додаванні розетки з розпізнаним протоколом (`driver_http_get_status()` — `main/driver_http.c`) пристрій одразу опитується на фактичний поточний стан (Shelly: `GET /relay/0` `"ison"` або `GET /rpc/Switch.GetStatus` `"output"`; Tasmota: `GET /cm?cmnd=Power1` `"POWER1"/"POWER"`), тож нова розетка не завжди стартує як "вимкнена" — якщо опитування не вдалося (мережа, нерозпізнаний протокол), стан за замовчуванням лишається "вимкнено", як і раніше. Тому чекбокс "Увімкнена" прибрано з форми додавання (він про робочий стан розетки, а не про намір) — на формі редагування він лишається, бо там це вже реальне поточне значення.
  Той самий запит виконується й для розеток, уже збережених у `config.json`, — одноразово при кожному завантаженні прошивки, а не тільки в момент додавання. `initial_status_task` (`main/plug_manager.c`) стартує разом з `plug_manager_init()`, чекає (до 30с, з кроком 1с) поки `wifi_manager_is_connected()` підтвердить STA-з'єднання — на старті прошивки під'єднання до Wi-Fi ще триває асинхронно, тож опитувати нема що, поки IP не отримано — і виходить одразу, якщо `wifi_manager_sta_config_error()` показує, що STA й не підключиться (немає сенсу чекати повні 30с даремно). Далі — та сама дисципліна знімку-під-локом/мережевого-виклику-без-локу/оновлення-під-локом, що й у `metrics_poll_task`: усі HTTP-розетки з розпізнаним сімейством опитуються по черзі, `last_state` кожної оновлюється за фактичною відповіддю пристрою. Якщо пристрій не відповів (мережа, ще не увімкнений) — розетка лишається зі старим значенням за замовчуванням ("вимкнено"), як і раніше; це не позначається як помилка виконання команди. Задача одноразова: після проходу по всіх розетках сама себе видаляє (`vTaskDelete`), на відміну від `metrics_poll_task`, який працює по колу.
- **MQTT** — один спільний клієнт на весь пристрій (адреса брокера в системних налаштуваннях); кожна розетка має свій `cmd_topic` + `payload_on/off`, QoS, retain.
- **Zigbee** — `driver_zigbee.c` є заглушкою: команди повертають `ESP_ERR_NOT_SUPPORTED` і пишуться в журнал як помилка. Причина: звичайний ESP32-WROOM не має радіо 802.15.4. Коли з'явиться супутній Zigbee-координатор (наприклад ESP32-H2/C6 по UART, або esp-zigbee-sdk), реалізацію можна додати всередину `driver_zigbee_set()` — схема конфігурації розетки (`plug_t.zigbee`), сховище, веб-морда (пункт "Zigbee" вже є в селекторі драйвера) і диспетчер у `plug_manager.c` міняти не потрібно.

## Моніторинг споживання

Для HTTP-розеток із розпізнаним протоколом і апаратним вимірюванням споживання (Shelly Plug/PlugS, Shelly Plus/Pro Plug S, Tasmota-прошивки на чипах з енергомонітором, наприклад Sonoff S31/POWR3) веб-морда показує під назвою розетки потужність (і напругу/струм, де прошивка їх віддає):

- **`driver_http_get_metrics()`** (`main/driver_http.c`) опитує сімейно-специфічний ендпоінт: Shelly Gen1 — `GET /status` (`meters[0].power`, без напруги/струму — Gen1-метеринг їх не вимірює), Shelly Gen2+ — той самий `GET /rpc/Switch.GetStatus?id=0`, що й запит статусу (`apower`/`voltage`/`current`), Tasmota — `GET /cm?cmnd=Status8` (`StatusSNS.ENERGY.{Power,Voltage,Current}`). ESPHome і нерозпізнані пристрої пропускаються (`ESP_ERR_NOT_SUPPORTED`) — так само, як і запит стану при додаванні.
- **`metrics_poll_task`** (`main/plug_manager.c`) опитує всі увімкнені HTTP-розетки з розпізнаним сімейством раз на 15с у фоновій задачі, без утримання `s_lock` під час самих HTTP-запитів (та сама дисципліна, що й у `do_dispatch()`/`plug_manager_add()`). Якщо пристрій не відповів на конкретний опит (мережа, таймаут) — попереднє значення лишається на місці (не блимає "порожнім" через один невдалий опит); якщо пристрій відповів, але не вміє вимірювати (наприклад звичайне Shelly1 реле) — показники обнуляються (`valid:false`), картку просто не показуємо.
- Веб-морда (`GET /api/plugs`, поле `metrics`) підвантажує список розеток кожні 10с у фоні (призупинено, поки відкрита форма редагування/додавання, щоб фонове оновлення не "вирвало" картку з-під користувача) — так свіжі покази з'являються без ручного натискання "Оновити".

## Автопошук у мережі

Кнопка "Знайти в мережі" (вкладка Розетки) робить дворівневий скан підмережі, до якої підключений хаб через STA:

**Пошук безперервний, а не одноразовий.** Один прохід підмережі іноді не знаходить пристрій — він міг ще завантажуватись, один ICMP-пакет міг загубитись по Wi-Fi, ARP міг ще не встигнути розв'язатись — і раніше єдиним виходом було натискати "Почати пошук" знову вручну. Тепер `net_scan_task` (`main/net_scan.c`) після натискання "Почати пошук" зациклюється: прохід за проходом пінгує підмережу, доки не буде натиснуто "Завершити пошук", обрано рядок зі списку, чи не спрацює запобіжник — 10 хвилин без зупинки (`SCAN_MAX_RUNTIME_MS`), про всяк випадок, якщо вкладку браузера просто закрили, не натиснувши "Завершити". Кожен знайдений хост запам'ятовується за IP і в наступних проходах більше не пінгується й не фінгерпринтиться повторно — список лише поповнюється, ніколи не дублюється й не зникає. `GET /api/scan` додатково повертає `pass` (номер поточного проходу), веб-морда показує його в статусі.

**Обмеження навантаження на ping-компонент.** Кожна ping-сесія (`ping/ping_sock.h`) — це власна FreeRTOS-задача й сокет на час життя. Реальний лог з пристрою показав `esp_ping_new_session(): create ping task failed` десятками разів **вже в перші ~800мс першого проходу** — тобто це не поступове виснаження за багато проходів (як спершу здавалось), а брак вільної внутрішньої SRAM з самого початку. Найімовірніша причина: `metrics_poll_task` (моніторинг споживання, доданий тієї ж сесії, що й безперервний скан) став уже **четвертою** задачею, яка постійно тримає зарезервованим стек 12288 байт під `esp_http_client` (поряд з `plug_worker`, HTTP-сервером і самим `net_scan_task`) — задача займає свій стек на весь час життя, працює вона в цю мить чи просто спить у `vTaskDelay`. На ESP32-S3-WROOM-1 стеки задач не можуть виділятись з PSRAM, лише з internal SRAM (~170KB усього) — і ці ~48KB, зарезервовані назавжди під чотири задачі, майже не лишають запасу на короткочасний сплеск із декількох додаткових 3072-байтних ping-задач одразу.

Тому `CONCURRENCY` (скільки ping-сесій відкрито одночасно) спершу знижено з 4 до 2, потім тимчасово до 1 (повністю послідовний пінг), поки помилка не стихла зовсім. `net_scan_task` тепер логує вільну internal SRAM (`heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`) перед стартом кожного скану — і на реальному пристрої це показало **50+ KB вільно**, набагато більше, ніж очікувалось. Це означає, що причина — не постійна стеля памʼяті, а рідкісний, короткочасний збіг у часі (усі залишкові помилки при CONCURRENCY=2 трапились саме навколо одноразової фонової синхронізації часу по NTP, яка теж використовує сокети/буфери). Сама помилка при цьому й раніше, і зараз не критична — хост, якому не вдалось відкрити ping-сесію, просто рахується як "без відповіді" й буде повторно перевірений за `SCAN_RETRY_STRIDE` проходів, як і будь-який інший мовчазний хост — але `esp_ping_new_session()` логує її на рівні ERROR з боку самого компонента `ping_sock`, тож `net_scan_init()` додатково глушить тег `"ping_sock"` (`esp_log_level_set`), щоб уже оброблена, непроблемна ситуація не виглядала в консолі як щось, що варто занепокоєння.

**Компроміс швидкість/надійність.** CONCURRENCY=1 повністю усунув помилку, але й уповільнив прохід підмережі до ~70с (майже вчетверо повільніше за початкову, "небезпечну" поведінку). Оскільки решта помилок при CONCURRENCY=2 виявилась рідкісним збігом у часі, а не стелею — піднято назад до **2**: цього достатньо, щоб різко знизити ризик порівняно з початковими 4, і водночас повернути прийнятну швидкість. Додатково скорочено таймаут очікування відповіді на пінг (`PING_TIMEOUT_MS`, 250→120мс — на локальній мережі реальна відповідь зазвичай приходить за одиниці-десятки мс, тож це не мало б помітно впливати на точність, а пропущений через це пристрій усе одно повторно перевіриться за `SCAN_RETRY_STRIDE` проходів) і паузу між партіями пінгів усередині проходу (`SCAN_BATCH_BREATHER_MS`, 30→15мс). Разом це повертає швидкість проходу приблизно до рівня початкової, "небезпечної" поведінки (~16-17с на /24), але вже з запасом по надійності: вдвічі менший пік конкуренції за ping-сесії, паузи між партіями/проходами, обмеження повторних спроб мовчазних хостів (`SCAN_RETRY_STRIDE`) і приглушене логування самого компонента. Пауза між проходами (`SCAN_PASS_IDLE_MS`, 2.5с) лишилась без змін; а з другого проходу й далі хости, які ще жодного разу не відповіли, пінгуються не щопроходу, а лише в одному з кожних `SCAN_RETRY_STRIDE` (=3) проходів, щоб не гамселити ті самі ~250 переважно порожніх адрес постійно. Перший прохід завжди повний.

1. **`net_scan.c`** — пінг-скан підмережі (обмежено /24, до ~254 адрес; пачками по 4 паралельно через `ping/ping_sock.h`), кожна відповідь додатково перевіряється швидким TCP-конектом на порт 80.
2. **Зворотний DNS (PTR), двоступенево** — для кожного хоста, що відповів на пінг (незалежно від :80):
   1. Спершу unicast-запит до DNS-сервера, який STA отримав по DHCP (зазвичай сам роутер): `<ip>.in-addr.arpa` → PTR. Працює, якщо роутер сам проксіює локальні PTR-запити для власних DHCP-клієнтів (типово для dnsmasq/OpenWrt).
   2. **На практиці велика частка роутерів (особливо mesh/побутові) цього не підтримує** — навіть якщо в адмінці роутера видно назви пристроїв (там вони часто беруться з DHCP lease table або хмарного сервісу виробника, а не з чогось, що можна опитати по мережі). Тому якщо крок 1 не дав відповіді — запит повторюється як mDNS: той самий PTR-запит, але multicast на `224.0.0.251:5353` з виставленим бітом "QU" (запит на unicast-відповідь, RFC 6762) — телефони (Android/iOS), ноутбуки (Bonjour/avahi) і частина прошивок розеток (Shelly Gen2+, ESPHome) мають вбудований mDNS-респондер і відповідають напряму, навіть коли роутер мовчить.

   Якщо пристрій взагалі ніколи не афішував собі імені (ні по DHCP, ні по mDNS) — поле `name` лишається порожнім, як і раніше з нерозпізнаним фінгерпринтом.
3. **`fingerprint.c`** — для кожного хоста з відкритим :80 послідовно пробує (кожен запит із заголовком `Connection: close` і таймаутом `CONFIG_FINGERPRINT_HTTP_TIMEOUT_MS`, за замовчуванням 800мс):
   - `GET /shelly` → Shelly (поле `gen` вирізняє Gen1 від Gen2+; Gen2/Gen3/новіші оброблюються однаково — RPC ідентичний);
   - `GET /cm?cmnd=Status%200` (+ `GET /cm?cmnd=Template` для моделі) → Tasmota, з евристикою по `POWER1..4`/`ENERGY`/`Dimmer` для типу пристрою;
   - `GET /` з пошуком "ESPHome" у тілі + спробою знайти `/switch/<id>/` в HTML → ESPHome (лише якщо в `menuconfig` увімкнено `CONFIG_FINGERPRINT_ENABLE_ESPHOME`, за замовчуванням так).

   Розпізнаний пристрій одразу дає готовий шаблон `on_url`/`off_url` (Shelly Gen1: `/relay/0?turn=on|off`; Gen2+: `/rpc/Switch.Set?id=0&on=true|false`; Tasmota: `/cm?cmnd=Power1%20On|Off`; ESPHome: `POST /switch/<id>/turn_on|turn_off`, якщо id вдалось знайти). У списку результатів це видно як бейдж з назвою прошивки (і моделлю в підказці), клік по рядку одразу підставляє ці URL у форму розетки — на відміну від нерозпізнаних хостів, де підставляється лише голий `http://<ip>/`, як і раніше.

**Це не повна автоконфігурація "знайшов → підключив без участі людини".** Каскад лише впізнає протокол/модель і формує URL для **першого/єдиного каналу** (Shelly `id=0`, Tasmota `Power1`) — багатоканальні прилади (силові стрічки, реле на кілька виходів) розпізнаються як `kind: "relay"` з приміткою біля бейджа, і URL для каналів 2+ треба донастроїти вручну. Якщо на пристрої встановлено пароль — це видно (`needs_auth`/"потрібен пароль" у списку), але Basic Auth для Tasmota, увімкнена нативно через query-параметри (`?user=...&password=...`), а не HTTP Basic — це поки не реалізовано, пароль доведеться ввести вручну в полях авторизації форми.

**Обмеження області видимості:** скан бачить лише пристрої в тій самій L2-підмережі, що й STA-інтерфейс хаба (той самий Wi-Fi, та сама підмережа/VLAN). Пристрої, підключені до вбудованої точки доступу хаба (192.168.4.x), чи в іншій підмережі/VLAN будинку — не знайде. Якщо STA не підключено, кнопка поверне помилку.

**Свідомо не перенесено з початкового технічного завдання на цю функцію** (щоб не роздувати проєкт компонентами й крихкими залежностями від внутрішніх API):
- **mDNS-браузинг** (`_shelly._tcp`, `_esphomelib._tcp`, `_http._tcp`) — прискорив би виявлення пристроїв, що самі анонсують сервіс, але додає ще один керований компонент (`espressif/mdns`, теж прибраний з ядра ESP-IDF v6.0.1) і ще один шлях збірки, який може зламатися. Ping+TCP:80+фінгерпринтинг уже покриває виявлення функціонально, просто трохи повільніше. *(Уточнення: для "назв" пристроїв (розділ вище) все ж таки додано мінімальний mDNS reverse-PTR запит вручну, без компонента `mdns` — це окремий, набагато простіший кейс: один UDP-пакет із зворотним запитом за вже відомою IP, а не повноцінний service browsing/анонсування.)*
- **ARP-скан через `etharp_request()`/`etharp_get_entry()` і кешування за MAC у NVS з TTL** — ці функції lwIP не є стабільним публічним API, і завʼязуватись на них ризиковано (та й ARP і так неявно відбувається під час пінгу). Замість цього результати скану живуть лише в оперативній памʼяті на час сесії; після перезавантаження роутера просто запускається новий скан.
- **Нативний бінарний API ESPHome (порт 6053, protobuf)** — це окремий немаленький протокол; підтримується лише REST-евристика через вбудований `web_server` ESPHome (якщо в YAML пристрою він увімкнений і містить `switch`-сутність).
- **Sonoff DIY (порт 8081, `POST /zeroconf/info`)** та **виявлення Tuya на стоковій прошивці** (порти 6668/6666/6667) — не реалізовані; перший через обмежений час на реалізацію, другий за узгодженою від початку умовою проєкту (Tuya/Smart Life свідомо не підтримуються).
- **Пріоритезація сканування за OUI-префіксами Espressif** — не потрібна: фінгерпринтинг і так запускається лише проти вже відфільтрованого списку хостів з відкритим :80, а не проти всієї підмережі.
- **Окремі vtable-драйвери на кожну прошивку** (`driver_shelly.c`/`driver_tasmota.c`/`driver_esphome.c`) — не додавались: Shelly/Tasmota/ESPHome REST — це завжди "звичайний HTTP GET/POST за URL", що вже й так робить `driver_http.c`; фінгерпринтинг лише підбирає правильний URL-шаблон і підставляє його в ту саму, вже наявну, форму HTTP-розетки. У формі розетки "Shelly (Gen1)"/"Shelly (Gen2+/Gen3)"/"Tasmota" тепер є окремими пунктами випадаючого списку драйвера (див. розділ "Драйвери") — це суто UI-рівнева зручність (не питати повний URL, а лише IP), під капотом усі три лишаються `driver=http` + `http.family`, без окремого коду виконання.

## Відомі спрощення / що варто допрацювати

- `status_url` в HTTP-драйвері поки не використовується для читання фактичного стану розетки (лише зберігається в конфігурації) — легко додати опитування статусу за потреби.
- NTP-клієнт "заряджається" один раз при старті через `esp_netif_sntp` — це нормально (SNTP сам періодично ресинхронізується у фоні), але явного "Синхронізувати зараз" в UI немає; за потреби легко додати кнопку, яка викликає `esp_netif_sntp_sync_wait`.
- Немає TLS/mTLS для HTTP чи MQTT (свідомо, за умовою задачі — лише прості HTTP/MQTT драйвери); за потреби `esp_http_client`/`esp-mqtt` підтримують `https://`/`mqtts://` без зміни архітектури.
- Автопошук — ping+TCP:80+фінгерпринтинг (Shelly/Tasmota/ESPHome), детальний список свідомо не реалізованого (mDNS, ARP/MAC-кеш, ESPHome native API, Sonoff DIY тощо) — див. розділ "Автопошук у мережі". Слухання MQTT discovery-топіків теж не реалізовано, але додається без зміни архітектури, якщо MQTT-брокер уже використовується для розеток.
- Вендорений `cJSON.c/h` — це не офіційна бібліотека DaveGamble/cJSON, а власна мінімальна реалізація з такою ж назвою функцій. Парсер толерантний до "сирого" JSON, який генерує сам пристрій, але не проходив повний conformance-тест (наприклад, юнікод-сурогатні пари `\uD8xx\uDCxx` не збираються в один кодпоінт — для ASCII-даних цього проєкту це не критично).
