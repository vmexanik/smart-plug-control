# Smart Plug Control (ESP32-S3-WROOM-1, ESP-IDF)

ESP32-S3-хаб для керування розумними розетками по **HTTP** та **MQTT** (Tuya/Xiaomi свідомо не підтримуються). Веб-морда для CRUD розеток, кнопка тестового вкл/викл, журнал подій з ротацією, 3 GPIO-входи (AC1/DC1/DC2) як тригери, системні налаштування з множинним вибором активних входів. Драйвер Zigbee закладений як заглушка на майбутнє.

Написано й перевірено проти **ESP-IDF v6.0.1** (у пісочниці немає xtensa-toolchain, тож збірку робив користувач локально — знайдені по ходу проблеми з `REQUIRES` вже виправлені, див. нижче).

**Апаратна платформа: ESP32-S3-WROOM-1-N16R8** (16MB флеш, 8MB Octal PSRAM). Проєкт починався на класичному ESP32-WROOM-32 і був перенесений на S3 — головні наслідки переносу: інші дефолтні GPIO для входів (`Kconfig.projbuild`, класичні 34/35/32 фізично зайняті під флеш/PSRAM на цьому модулі), окремий `sdkconfig.defaults.esp32s3` з увімкненим PSRAM (`CONFIG_SPIRAM=y`), і значно менше памʼяті-орієнтованих обмежень — `malloc()` понад 16KB (`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`) тепер прозоро йде в PSRAM, тож фрагментація/вичерпання внутрішньої SRAM, що раніше змушувала уважно проєктувати API (`net_scan_get_result()` по одному елементу замість одного великого масиву — див. коментар у `net_scan.h`), тепер значно менш імовірна. Радіо 802.15.4 (Zigbee/Thread) на S3, як і на класичному ESP32, немає — це лише в C6/H2.

**Відомий підводний камінь переносу:** розміри стеків задач, підібрані й перевірені на класичному ESP32 (Xtensa LX6), виявились замалими на S3 (Xtensa LX7) для задач, що викликають `esp_http_client` -- перший же реальний виклик (натискання on/off у веб-морді) провалював стек глибше за canary-зону перевірки переповнення, і замість зрозумілого повідомлення про це система падала з незрозумілою `Guru Meditation (LoadProhibited)` **всередині самого FreeRTOS-планувальника** (`prvSelectHighestPriorityTaskSMP`) з "отруєними" регістрами `0xa5a5a5a5` -- класичний відкладений симптом переповнення стека, що зачепило чужу структуру в памʼяті, а не сам винуватець. Стеки `plug_manager.c`'s `worker_task`, HTTP-сервера (`web_server.c`) і `net_scan.c`'s `net_scan_task` підняті з 8192 до 12288 байт; додатково увімкнено `CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK` (апаратний watchpoint, ловить запис в останні 32 байти стека будь-якої задачі точно в момент переповнення) — якщо колись знову не вистачить стека, буде чіткий панік з точним місцем, а не ця головоломка.

## Збірка та прошивка

```bash
idf.py set-target esp32s3
idf.py build
idf.py -p <PORT> flash monitor
```

Якщо проєкт раніше вже збирався під `esp32` (класичний WROOM-32) в цій самій теці, `set-target` сам перегенерує `sdkconfig` під новий чіп -- але про всяк випадок, якщо після цього щось не так (лишились старі значення), надійніше видалити його вручну і зібрати наново:

```bash
rm sdkconfig   # на Windows: del sdkconfig
idf.py set-target esp32s3
idf.py build
```

Компоненти `joltwallet/littlefs` та `espressif/mqtt` підтягнуться автоматично через `main/idf_component.yml` (component manager) при першому білді.

**Чому не стандартні `mqtt`/`json` компоненти ESP-IDF.** У ESP-IDF v6.0.1 обидва компоненти прибрані з ядра (перевірено діфом `.gitmodules` між версіями — submodule cJSON зник, а `components/mqtt` лишився порожньою заглушкою):
- `esp-mqtt` тепер підключається як керований компонент `espressif/mqtt` (додано в `idf_component.yml`, `REQUIRES` вказує на `espressif__mqtt` — саме таке ім'я отримує тека `managed_components/espressif__mqtt`).
- cJSON вендорено напряму в `main/cJSON.c/h` — мінімальна власна реалізація, що покриває рівно ті функції cJSON API, які реально використовуються в проєкті (`cJSON_Parse`, `cJSON_PrintUnformatted`, `cJSON_Add*ToObject`, `cJSON_Is*`, `cJSON_ArrayForEach` тощо). Це прибирає залежність від того, під яким іменем (якщо взагалі) Espressif надалі публікуватиме cJSON у реєстрі компонентів.

`esp_driver_gpio` (замість застарілого `driver`) звірено напряму проти тегу `v6.0.1` в репозиторії esp-idf — актуальна назва.

> Якщо `idf.py build` все ж лається на `REQUIRES component "X" not found` — залишок цього списку (`nvs_flash`, `esp_wifi`, `esp_netif`, `esp_event`, `esp_http_server`, `esp_http_client`, `esp_timer`) вже підтверджений реальним логом збірки користувача (впав лише на `mqtt`, решта резолвилась без помилок).

## Підключення входів

3 фіксовані логічні входи: **AC1, DC1, DC2**. GPIO-номери **не редагуються з веб-морди** — це свідоме рішення: вони прошиті через `menuconfig → Smart Plug Control → Default trigger input GPIOs` (за замовчуванням 34/35/32 — вхідні піни без підтяжки, підходять для опто-розв'язаних сигналів) і застосовуються через `storage_force_fixed_inputs()` (`main/storage.c`), яка перезаписує GPIO-поля кожного разу при завантаженні конфігу і при кожному збереженні системних налаштувань — навіть якщо в `config.json` чи в запиті до `/api/settings` прийде інше значення, воно ігнорується. Щоб змінити піни, треба перепрошити пристрій з новим `menuconfig`. З веб-морди редагується лише **чи слухати** кожен вхід (enable/disable), множинний вибір.

Логіка: **1 на вході → прив'язана розетка увімкнена, 0 → вимкнена**. Прапорець "інверсія" на кожній розетці інвертує це правило індивідуально (одна розетка на вході може бути "нормально відкритою", інша "нормально закритою"). Розетка може бути не прив'язана до жодного входу (`input = NONE`) — тоді керується лише вручну/через API.

**Розетка з прив'язаним входом керується виключно ним** — кнопка on/off на веб-морді для неї сіра/неактивна (`app.js`, `renderPlugRow()`), а `plug_manager_test_action()` (`main/plug_manager.c`) відхиляє ручну команду на бекенді теж (`ESP_ERR_INVALID_STATE`, `"plug is controlled by an input trigger, not manually"`) — це не лише UI-обмеження, той самий API-ендпоінт заблокований і для прямих запитів. Причина: вхід і ручна кнопка — це два незалежні джерела команд на те саме реле, і без цього правила останнє, що спрацювало (вхід чи клік), непередбачувано "перемагає" інше.

**Застосування стану входів при завантаженні прошивки** відбувається не одразу, а лише після підтвердженого STA-з'єднання — `plug_manager.c`'s `initial_status_task()` (той самий, що опитує реальний стан збережених HTTP-розеток при бут, див. вище) наприкінці викликає `plug_manager_sync_all_from_inputs()`, коли `wifi_manager_is_connected()` вже `true`. Раніше цей виклик робився з `app_main.c` одразу після фіксованої затримки 500мс — цього достатньо для стабілізації GPIO-дебаунсу, але зазвичай замало для отримання IP по Wi-Fi; команда на реле йшла в чергу й одразу впиралась у повний 5-секундний таймаут `driver_http_set()` через відсутність мережі, без жодної повторної спроби — реле лишалось у довільному стані з моменту вмикання живлення, ігноруючи фактичний рівень на (можливо інвертованому) вході. Якщо STA взагалі не підключається (невірний пароль чи AP-only режим) — застосування стану входів так само пропускається, як і опитування статусу розеток: без мережі однаково нема як подати команду на HTTP/MQTT-розетку.

## Веб-морда

`http://<ip-пристрою>/` — вкладки:

- **Розетки** — список, додавання/редагування/видалення, кругла іконка-кнопка живлення для ручного on/off (зелена/червона за поточним станом), індикатор останнього стану, потужність/напруга/струм під назвою для розеток з енергомонітором (див. розділ "Моніторинг споживання"), кнопка "Знайти в мережі" (див. розділ "Автопошук у мережі").
- **Системні налаштування** — які входи слухати (мультивибір; GPIO-піни, debounce і період опитування фіксовані прошивкою, тут лише для довідки), Wi-Fi (SSID/пароль STA), спільний MQTT-брокер, дата і час (лише ручне встановлення — NTP-сервер задається в прошивці), параметри ротації журналу.
- **Журнал подій** — останні N записів (джерело: input/manual/api/boot/system), очищення.

## Wi-Fi

Пристрій завжди піднімає AP `SmartPlug-XXXXXX` (пароль з Kconfig, за замовчуванням `plugsetup`) на `192.168.4.1` — це гарантує доступ до веб-морди навіть якщо STA не налаштована/недоступна. STA-креденшали зберігаються в NVS і застосовуються без перепришивки через вкладку "Системні налаштування" (розділ Wi-Fi).

Поле пароля на вкладці налаштувань підвантажує поточний збережений пароль (кнопка "Показати"/"Сховати" перемикає видимість) — раніше поле завжди було порожнім, тож натискання "Підключити" без повторного вводу пароля відправляло порожній рядок і затирало робочі креденшали. Веб-морда цього пристрою не має власної автентифікації (будь-хто в тій самій мережі й так може змінити налаштування), тож повернення пароля назад у відповіді `GET /api/wifi` не є новою діркою в безпеці.

Кнопка "Знайти мережі" запускає `esp_wifi_scan_start()` (блокуючий виклик у власній задачі — `wifi_scan_task` в `wifi_manager.c`) і показує знайдені мережі списком (клік по рядку — як і у пошуку розеток, без окремої кнопки-дії): лише SSID і позначка "відкрита" для мереж без пароля (рівень сигналу свідомо не визначається й не показується — для вибору мережі він не потрібен, а зайве поле лише ускладнює список). Мережі з однаковим SSID (типово — mesh/декілька точок доступу) дедуплікуються: лишається перше входження, бо `esp_wifi_scan_get_ap_records()` вже повертає список відсортованим за RSSI (найсильніший сигнал першим), навіть якщо сам застосунок це значення більше ніде не зберігає. Приховані мережі (порожній SSID) не показуються — такий SSID можна ввести вручну, поле не заблоковане тільки для вибору зі списку. Сканування триває секунди й, за документацією Espressif, не розриває вже активне STA-з'єднання (типовий час на канал ~120мс, значно менше порогу ~1500мс, після якого можливий розрив).

**Перепідключення після розриву** (`wifi_manager.c`, функція `event_handler()`) розрізняє дві категорії причин розриву:

- **Реальна проблема з обліковими даними** (`is_hard_auth_failure_reason()`: `WIFI_REASON_AUTH_FAIL`, `WIFI_REASON_MIC_FAILURE`, `WIFI_REASON_4WAY_HANDSHAKE_TIMEOUT` тощо) — це може статись лише після того, як AP вже знайдено й почалась спроба автентифікації, тож якщо це стається — це справді невірний пароль. Після 3 таких підряд (`STA_CONFIG_ERROR_MAX_RETRIES`) автоперепідключення зупиняється (`config_error` в `/api/status`/`/api/wifi` стає `true`, веб-морда показує попередження) — сенсу продовжувати спроби немає.
- **`WIFI_REASON_NO_AP_FOUND`** (і кілька суміжних кодів, `is_ap_not_found_reason()`) — цей код неоднозначний: він же виникає і при справжній помилці в SSID (типо при першому налаштуванні), і при тимчасовому зникненні мережі, яка щойно нормально працювала (перезавантаження роутера, коротка перерва зв'язку) — фізично неможливо відрізнити ці два випадки лише за кодом причини. Розрізняється за історією: якщо з поточними обліковими даними хоч раз вдавалось отримати IP (`s_sta_ever_connected`), `NO_AP_FOUND` після цього трактується як тимчасове й ретраїться без обмежень — так само, як звичайний нормальний пристрій (напр. розетка Shelly) сам знаходить мережу, щойно вона знову з'явиться. Лічильник із 3 спробами застосовується до `NO_AP_FOUND` лише поки ці облікові дані ще жодного разу не спрацювали (типовий сценарій — одруківка в SSID під час першого налаштування).

Обидва лічильники й `s_sta_ever_connected` скидаються при новій спробі зберегти облікові дані з форми або при перезавантаженні.

## Дата і час

ESP32 без RTC-батареї стартує з часом 1970-01-01 (epoch 0). `time_sync.c` (обгортка над `esp_netif_sntp`) неблокуюче "заряджає" NTP-клієнт при старті проти сервера з `CONFIG_NTP_SERVER_DEFAULT` (`menuconfig → Smart Plug Control → NTP server`, за замовчуванням `pool.ntp.org`) — **сервер не редагується з веб-морди**, лише перепрошивкою з новим `menuconfig`, за тим самим принципом, що й GPIO-піни входів. Фактична синхронізація відбувається, щойно STA отримає IP і зможе достукатись до сервера. Якщо інтернету немає (лише AP-режим) або `CONFIG_NTP_SERVER_DEFAULT` порожній — час можна виставити вручну через вкладку "Системні налаштування" (поле "Встановити вручну" → `POST /api/time`, це окрема, незалежна від NTP дія). Журнал подій (`event_log.c`) пише `time(NULL)` — тобто мітки будуть коректними лише після синхронізації одним із цих двох способів; до того — це відлік від 1970 року, але видно статус (`synced`/`source` через `GET /api/time`) і є спосіб це виправити без очікування.

## Драйвери

- **HTTP** — окремі `on_url`/`off_url` (GET або POST), опційний Basic Auth, опційний `status_url` (зарезервований, наразі не опитується автоматично). У формі розетки поле "Драйвер / протокол" тепер, крім HTTP/MQTT/Zigbee, напряму пропонує **Shelly (Gen1)**, **Shelly (Gen2+/Gen3)** і **Tasmota** окремими пунктами (усі три технічно все ще виконуються через `driver_http.c` — це `driver=http` з заданим `http.family`, окремого виконавчого коду на кожну прошивку немає й не планується, див. пункт нижче в "Свідомо не перенесено"). Вибір такого пункту ховає поля URL і замінює їх на єдине поле "IP або хост пристрою" — адреси `on_url`/`off_url` генеруються на льоту в браузері за тим самим шаблоном, що й `fingerprint.c` при скані (`app.js: FAMILY_URL_TEMPLATES`). Якщо розетку додано через "Знайти в мережі" і протокол розпізнано автоматично — той самий пункт вибирається сам, поле хоста підставляється з IP знахідки. Для нерозпізнаних пристроїв (ручне додавання, ESPHome) URL лишаються звичайними текстовими полями.
  При додаванні розетки з розпізнаним протоколом (`driver_http_get_status()` — `main/driver_http.c`) пристрій одразу опитується на фактичний поточний стан (Shelly: `GET /relay/0` `"ison"` або `GET /rpc/Switch.GetStatus` `"output"`; Tasmota: `GET /cm?cmnd=Power1` `"POWER1"/"POWER"`), тож нова розетка не завжди стартує як "вимкнена" — якщо опитування не вдалося (мережа, нерозпізнаний протокол), стан за замовчуванням лишається "вимкнено", як і раніше. Тому чекбокс "Увімкнена" прибрано з форми додавання (він про робочий стан розетки, а не про намір) — на формі редагування він лишається, бо там це вже реальне поточне значення.
  Той самий запит виконується й для розеток, уже збережених у `config.json`, — одноразово при кожному завантаженні прошивки, а не тільки в момент додавання. `initial_status_task` (`main/plug_manager.c`) стартує разом з `plug_manager_init()`, чекає (до 30с, з кроком 1с) поки `wifi_manager_is_connected()` підтвердить STA-з'єднання — на старті прошивки під'єднання до Wi-Fi ще триває асинхронно, тож опитувати нема що, поки IP не отримано — і виходить одразу, якщо `wifi_manager_sta_config_error()` показує, що STA й не підключиться (немає сенсу чекати повні 30с даремно). Далі — та сама дисципліна знімку-під-локом/мережевого-виклику-без-локу/оновлення-під-локом, що й у `metrics_poll_task`: усі HTTP-розетки з розпізнаним сімейством опитуються по черзі, `last_state` кожної оновлюється за фактичною відповіддю пристрою. Якщо пристрій не відповів (мережа, ще не увімкнений) — розетка лишається зі старим значенням за замовчуванням ("вимкнено"), як і раніше; це не позначається як помилка виконання команди. Задача одноразова: після проходу по всіх розетках сама себе видаляє (`vTaskDelete`), на відміну від `metrics_poll_task`, який працює по колу.
- **MQTT** — один спільний клієнт на весь пристрій (адреса брокера в системних налаштуваннях); кожна розетка має свій `cmd_topic` + `payload_on/off`, QoS, retain.
- **Zigbee** — `driver_zigbee.c` є заглушкою: команди повертають `ESP_ERR_NOT_SUPPORTED` і пишуться в журнал як помилка. Причина: звичайний ESP32-WROOM не має радіо 802.15.4. Коли з'явиться супутній Zigbee-координатор (наприклад ESP32-H2/C6 по UART, або esp-zigbee-sdk), реалізацію можна додати всередину `driver_zigbee_set()` — схема конфігурації розетки (`plug_t.zigbee`), сховище, веб-морда (пункт "Zigbee" вже є в селекторі драйвера) і диспетчер у `plug_manager.c` міняти не потрібно.

## Моніторинг споживання

Для HTTP-розеток із розпізнаним протоколом і апаратним вимірюванням споживання (Shelly Plug/PlugS, Shelly Plus/Pro Plug S, Tasmota-прошивки на чипах з енергомонітором, наприклад Sonoff S31/POWR3) веб-морда показує під назвою розетки потужність (і напругу/струм, де прошивка їх віддає):

- **`driver_http_get_metrics()`** (`main/driver_http.c`) опитує сімейно-специфічний ендпоінт: Shelly Gen1 — `GET /status` (`meters[0].power`, без напруги/струму — Gen1-метеринг їх не вимірює), Shelly Gen2+ — той самий `GET /rpc/Switch.GetStatus?id=0`, що й запит статусу (`apower`/`voltage`/`current`), Tasmota — `GET /cm?cmnd=Status8` (`StatusSNS.ENERGY.{Power,Voltage,Current}`). ESPHome і нерозпізнані пристрої пропускаються (`ESP_ERR_NOT_SUPPORTED`) — так само, як і запит стану при додаванні.
- **`metrics_poll_task`** (`main/plug_manager.c`) опитує всі увімкнені HTTP-розетки з розпізнаним сімейством раз на 10с у фоновій задачі (`METRICS_POLL_INTERVAL_MS`, узгоджено з інтервалом автооновлення веб-морди нижче), без утримання `s_lock` під час самих HTTP-запитів (та сама дисципліна, що й у `do_dispatch()`/`plug_manager_add()`). Якщо пристрій не відповів на конкретний опит (мережа, таймаут) — попереднє значення лишається на місці (не блимає "порожнім" через один невдалий опит); якщо пристрій відповів, але не вміє вимірювати (наприклад звичайне Shelly1 реле) — показники обнуляються (`valid:false`), картку просто не показуємо.
- Веб-морда (`GET /api/plugs`, поле `metrics`) підвантажує список розеток кожні 10с у фоні (призупинено, поки відкрита форма редагування/додавання, щоб фонове оновлення не "вирвало" картку з-під користувача) — свіжі покази з'являються без ручного натискання (кнопки "Оновити" на панелі розеток більше немає — оновлення суто автоматичне).
- **Той самий опит подвоює роль "чи розетка взагалі на зв'язку"** (`plug_t.reachable`, `main/app_types.h`) — успіх/невдача опиту метрик оновлює цей прапорець кожні 10с незалежно від самих показників. `do_dispatch()` (`main/plug_manager.c`) звіряється з ним перед будь-якою командою on/off: якщо розетка з розпізнаним сімейством помічена недоступною, мережевий виклик взагалі не робиться (замість блокування на кількасекундному таймауті `esp_http_client`) — натомість одразу повертається `"plug not reachable (offline)"`. Це навмисно обмежено саме розпізнаним HTTP-сімейством: лише для нього є фоновий опит, який згодом сам поверне прапорець у `true`, щойно пристрій знову відповість, — для розеток з довільним URL (нерозпізнаний протокол), MQTT чи Zigbee такого фонового опиту немає, тож для них `reachable` завжди `true` (інакше кнопка керування могла б застрягти вимкненою назавжди, бо ніщо й ніколи не перевірить пристрій повторно). У веб-морді кнопка on/off такої розетки сіріється й неактивна (`app.js`, `renderPlugRow()`), замість того щоб дозволяти накопичувати черги невдалих спроб при повторних натисканнях.
- **Перепідключення розетки → повторна перевірка стану.** `last_state` інакше оновлюється лише при командах, які надіслав сам пристрій (`do_dispatch()`) — тож поки розетка була недоступна, будь-яка зміна її фактичного стану (фізична кнопка на корпусі, втрата живлення й новий стан за замовчуванням, керування ще звідкись) лишилась би непоміченою: після відновлення зв'язку веб-морда й далі показувала б те, що було до збою. Тому в момент, коли `metrics_poll_task` бачить перехід `reachable` з `false` у `true` (тобто саме зараз, а не на кожному опиті), додатково викликається `driver_http_get_status()` — той самий запит, що й при першому додаванні розетки чи при завантаженні прошивки (`initial_status_task`) — і `last_state`/`last_cmd_ok` оновлюються за фактичною відповіддю пристрою. У журнал подій пишеться запис `LOG_SRC_SYSTEM` з деталлю `"reconnected, state re-checked"`.

## Автопошук у мережі

Кнопка "Знайти в мережі" (вкладка Розетки) робить трирівневий скан підмережі, до якої підключений хаб через STA:

**Пошук безперервний, а не одноразовий.** Один прохід підмережі іноді не знаходить пристрій — він міг ще завантажуватись, один пакет міг загубитись по Wi-Fi, ARP міг ще не встигнути розв'язатись — і раніше єдиним виходом було натискати "Почати пошук" знову вручну. Тепер `net_scan_task` (`main/net_scan.c`) після натискання "Почати пошук" зациклюється: прохід за проходом опитує підмережу, доки не буде натиснуто "Завершити пошук", обрано рядок зі списку, чи не спрацює запобіжник — 10 хвилин без зупинки (`SCAN_MAX_RUNTIME_MS`), про всяк випадок, якщо вкладку браузера просто закрили, не натиснувши "Завершити". Кожен знайдений хост запам'ятовується за IP і в наступних проходах більше не перевіряється й не фінгерпринтиться повторно — список лише поповнюється, ніколи не дублюється й не зникає. `GET /api/scan` додатково повертає `pass` (номер поточного проходу), веб-морда показує його в статусі.

**Активний ARP-пробінг як основний, а не запасний, спосіб виявлення.** Раніше основним механізмом був ping-скан (з пасивним читанням ARP-кешу як запасним варіантом для хостів, що мовчать на ICMP/TCP) — тепер навпаки: ARP-резолюція запускається навмисно й першою для кожної адреси підмережі, а ping лишається лише другорядним, суто інформаційним підтвердженням для вже знайдених хостів. Причина: NIC пристрою мусить відповідати на ARP для базової L2-звʼязності — без цього мережа не працює взагалі — тоді як ICMP echo й TCP SYN значно частіше свідомо ігноруються (дефолтний файрвол Windows, чимала частка IoT-прошивок). Раніше такі хости пошук просто не бачив, доки не додали пасивне читання ARP-кешу як фолбек; тепер це основний шлях виявлення для всіх хостів, а не лише для тих, що випадково "просочились" повз файрвол.

Технічна реалізація навмисно **не** використовує lwIP-функцію `etharp_request()` напряму — це вимагало б або передавати `struct netif*` (сирий вказівник lwIP, не той `esp_netif_t*`, що є в решті проєкту), або `esp_netif_get_netif_impl()`, чий власний заголовок прямо каже "supposed to be called only from internals of TCP/IP stack". Замість цього `arp_probe_batch()` (`main/net_scan.c`) використовує єдиний UDP-сокет (один на всю сесію скану, `SOCK_DGRAM`) і робить звичайний `sendto()` на кожну адресу-кандидата, на довільний, майже напевно нікому не потрібний порт (`ARP_PROBE_UDP_PORT`) — вміст пакета й будь-яка відповідь (їх зазвичай і нема, порт ніхто не слухає) повністю ігноруються. Сенс лише в тому, що перш ніж lwIP зможе взагалі спробувати відправити цей UDP-пакет, він мусить розв'язати MAC-адресу цілі через ARP — той самий механізм, на який раніше побічно спирались ping/TCP:80, тепер викликається напряму через повністю публічний BSD sockets API, без жодної lwIP-внутрішньої функції. `sendto()` не блокується в очікуванні цієї резолюції (lwIP чергує пакет і резолвить у фоні на tcpip-треді), тож ціла партія адрес пробується практично миттєво одна за одною. Сокет прив'язується (`bind`) до IP самої STA — той самий запобіжник, що й у `dns_ptr_query()` нижче: пристрій працює в режимі APSTA (власна точка доступу завжди піднята поруч зі STA), і без явного `bind` вихідний пакет міг би так само легко піти через SoftAP-інтерфейс замість реальної LAN STA.

**Читання ARP-кешу** (`arp_dump_snapshot()`, `main/net_scan.c`) лишається тим самим механізмом, що й раніше — саме він і перетворює "запит відправлено" на "хост знайдено": після кожної партії `sendto()`-проб пауза `ARP_SETTLE_MS` (200мс, дати відповідям осісти), потім читання таблиці. У ESP-IDF `LWIP_TCPIP_CORE_LOCKING` вимкнено за замовчуванням, тож `LOCK_TCPIP_CORE()`/`UNLOCK_TCPIP_CORE()` — порожні макроси, не справжній мʼютекс; викликати `etharp_get_entry()` напряму з задачі сканування означало б гонку з tcpip-тредом. Правильний спосіб — `tcpip_callback()`: переносить функцію на сам tcpip-тред і виконує її там, де жодне блокування вже не потрібне; задача сканування чекає на семафор (з таймаутом-запобіжником), поки той відпрацює. Розмір таблиці ARP у lwIP (`ARP_TABLE_SIZE`) на цій платформі фіксований у 10 записів і **не виведений у Kconfig ESP-IDF** (перевірено — такого пункту немає ні в `components/lwip/Kconfig`, ні деінде) — підняти його без форку компонента непросто. Тому партія проб обмежена `ARP_PROBE_BATCH_SIZE` (=8, з запасом під 10) і дамп робиться одразу після кожної такої партії, а не одноразово в кінці проходу — інакше на /24-скані більшість записів встигне витіснитися задовго до завершення.

**Ping — тепер лише другорядне, інформаційне підтвердження.** Для кожного щойно знайденого через ARP хоста виконується один одиночний пінг (`do_single_ping()`) — не для того, щоб вирішити, чи включати хост у результати (ARP вже це довів), а щоб показати в UI, чи відповідає він ще й на ICMP (позначка "без ping" біля IP, якщо ні — типово для файрволу чи деяких IoT-прошивок). Це прибрало стару паралельну (`CONCURRENCY`) інфраструктуру одночасних ping-сесій повністю: раніше пінгувалась уся підмережа (до ~254 адрес щопроходу) паралельними пачками, що й було першопричиною помилок `esp_ping_new_session(): create ping task failed` під навантаженням (детальний розбір цього багу — нижче, лишений як історія діагностики). Тепер пінгуються лише вже підтверджені ARP-ом хости (типово одиниці-десятки на домашній LAN), по одному, без паралелізму — і оскільки це більше не єдиний спосіб знайти хост, а лише необов'язковий інформаційний штрих, невдала ping-сесія (`esp_ping_new_session()` не вдалась) просто лишає `ping_ok: false`, хост однаково залишається в списку.

<details>
<summary>Історія діагностики: чому раніше ping-скан ламався під навантаженням (архівний розбір, актуальний лише для старої, ping-первинної архітектури)</summary>

**Обмеження навантаження на ping-компонент.** Кожна ping-сесія (`ping/ping_sock.h`) — це власна FreeRTOS-задача й сокет на час життя. Реальний лог з пристрою показав `esp_ping_new_session(): create ping task failed` десятками разів **вже в перші ~800мс першого проходу** — тобто це не поступове виснаження за багато проходів (як спершу здавалось), а брак вільної внутрішньої SRAM з самого початку. Найімовірніша причина: `metrics_poll_task` (моніторинг споживання, доданий тієї ж сесії, що й безперервний скан) став уже **четвертою** задачею, яка постійно тримає зарезервованим стек 12288 байт під `esp_http_client` (поряд з `plug_worker`, HTTP-сервером і самим `net_scan_task`) — задача займає свій стек на весь час життя, працює вона в цю мить чи просто спить у `vTaskDelay`. На ESP32-S3-WROOM-1 стеки задач не можуть виділятись з PSRAM, лише з internal SRAM (~170KB усього) — і ці ~48KB, зарезервовані назавжди під чотири задачі, майже не лишають запасу на короткочасний сплеск із декількох додаткових 3072-байтних ping-задач одразу.

Тодішній `CONCURRENCY` (скільки ping-сесій відкрито одночасно) спершу знижено з 4 до 2, потім тимчасово до 1 (повністю послідовний пінг), поки помилка не стихла зовсім. `net_scan_task` тепер логує вільну internal SRAM (`heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`) перед стартом кожного скану — і на реальному пристрої це показало **50+ KB вільно**, набагато більше, ніж очікувалось. Це означає, що причина — не постійна стеля памʼяті, а рідкісний, короткочасний збіг у часі (усі залишкові помилки при CONCURRENCY=2 трапились саме навколо одноразової фонової синхронізації часу по NTP, яка теж використовує сокети/буфери). Сама помилка при цьому й раніше, і зараз не критична — хост, якому не вдалось відкрити ping-сесію, просто рахується як "без відповіді" — але `esp_ping_new_session()` логує її на рівні ERROR з боку самого компонента `ping_sock`, тож `net_scan_init()` досі глушить тег `"ping_sock"` (`esp_log_level_set`), щоб уже оброблена, непроблемна ситуація не виглядала в консолі як щось, що варто занепокоєння.

CONCURRENCY=1 повністю усунув помилку, але й уповільнив прохід підмережі до ~70с. Оскільки решта помилок при CONCURRENCY=2 виявилась рідкісним збігом у часі, а не стелею — піднято назад до 2. Це лишалось поточним станом, доки весь підхід не замінили на ARP-первинний вище — новий підхід прибирає першопричину повністю (ping більше не намагається достукатись до ~230 мовчазних адрес щопроходу), а не просто балансує симптом.

</details>

Нове орієнтовне співвідношення швидкості: партія з `ARP_PROBE_BATCH_SIZE` (=8) проб + `ARP_SETTLE_MS` (200мс) очікування — близько 32 партій на повний /24-прохід, ~6-7с лише на ARP-стадію; підтверджувальний пінг+TCP:80 виконуються тільки для реально знайдених хостів (типово одиниці-десятки), а не для всієї підмережі — сумарно прохід зазвичай трохи швидший за попередній ping-первинний підхід (~16-17с), і без ризику вичерпання ping-сесій, оскільки паралельних ping-сесій тепер узагалі нема. Пауза між проходами (`SCAN_PASS_IDLE_MS`, 2.5с) лишилась без змін; а з другого проходу й далі хости, які ще жодного разу не відповіли, пробуються не щопроходу, а лише в одному з кожних `SCAN_RETRY_STRIDE` (=3) проходів, щоб не гамселити ті самі ~250 переважно порожніх адрес постійно. Перший прохід завжди повний.

1. **`net_scan.c`** — активний ARP-пробінг підмережі (обмежено /24, до ~254 адрес; партіями по `ARP_PROBE_BATCH_SIZE`), кожен знайдений хост додатково перевіряється одиночним пінгом (інформаційно) і швидким TCP-конектом на порт 80.
2. **Зворотний DNS (PTR), двоступенево** — для кожного знайденого хоста (незалежно від :80):
   1. Спершу unicast-запит до DNS-сервера, який STA отримав по DHCP (зазвичай сам роутер): `<ip>.in-addr.arpa` → PTR. Працює, якщо роутер сам проксіює локальні PTR-запити для власних DHCP-клієнтів (типово для dnsmasq/OpenWrt).
   2. **На практиці велика частка роутерів (особливо mesh/побутові) цього не підтримує** — навіть якщо в адмінці роутера видно назви пристроїв (там вони часто беруться з DHCP lease table або хмарного сервісу виробника, а не з чогось, що можна опитати по мережі). Тому якщо крок 1 не дав відповіді — запит повторюється як mDNS: той самий PTR-запит, але multicast на `224.0.0.251:5353` з виставленим бітом "QU" (запит на unicast-відповідь, RFC 6762) — телефони (Android/iOS), ноутбуки (Bonjour/avahi) і частина прошивок розеток (Shelly Gen2+, ESPHome) мають вбудований mDNS-респондер і відповідають напряму, навіть коли роутер мовчить.

   Якщо пристрій взагалі ніколи не афішував собі імені (ні по DHCP, ні по mDNS) — поле `name` лишається порожнім, як і раніше з нерозпізнаним фінгерпринтом.
3. **`fingerprint.c`** — для кожного хоста з відкритим :80 послідовно пробує (кожен запит із заголовком `Connection: close` і таймаутом `CONFIG_FINGERPRINT_HTTP_TIMEOUT_MS`, за замовчуванням 800мс):
   - `GET /shelly` → Shelly (поле `gen` вирізняє Gen1 від Gen2+; Gen2/Gen3/новіші оброблюються однаково — RPC ідентичний);
   - `GET /cm?cmnd=Status%200` (+ `GET /cm?cmnd=Template` для моделі) → Tasmota, з евристикою по `POWER1..4`/`ENERGY`/`Dimmer` для типу пристрою;
   - `GET /` з пошуком "ESPHome" у тілі + спробою знайти `/switch/<id>/` в HTML → ESPHome (лише якщо в `menuconfig` увімкнено `CONFIG_FINGERPRINT_ENABLE_ESPHOME`, за замовчуванням так).

   Розпізнаний пристрій одразу дає готовий шаблон `on_url`/`off_url` (Shelly Gen1: `/relay/0?turn=on|off`; Gen2+: `/rpc/Switch.Set?id=0&on=true|false`; Tasmota: `/cm?cmnd=Power1%20On|Off`; ESPHome: `POST /switch/<id>/turn_on|turn_off`, якщо id вдалось знайти). У списку результатів це видно як бейдж з назвою прошивки (і моделлю в підказці), клік по рядку одразу підставляє ці URL у форму розетки — на відміну від нерозпізнаних хостів, де підставляється лише голий `http://<ip>/`, як і раніше.

**Це не повна автоконфігурація "знайшов → підключив без участі людини".** Каскад лише впізнає протокол/модель і формує URL для **першого/єдиного каналу** (Shelly `id=0`, Tasmota `Power1`) — багатоканальні прилади (силові стрічки, реле на кілька виходів) розпізнаються як `kind: "relay"` з приміткою біля бейджа, і URL для каналів 2+ треба донастроїти вручну. Якщо на пристрої встановлено пароль — це видно (`needs_auth`/"потрібен пароль" у списку), але Basic Auth для Tasmota, увімкнена нативно через query-параметри (`?user=...&password=...`), а не HTTP Basic — це поки не реалізовано, пароль доведеться ввести вручну в полях авторизації форми.

**Обмеження області видимості:** скан бачить лише пристрої в тій самій L2-підмережі, що й STA-інтерфейс хаба (той самий Wi-Fi, та сама підмережа/VLAN). Пристрої, підключені до вбудованої точки доступу хаба (192.168.4.x), чи в іншій підмережі/VLAN будинку — не знайде. Якщо STA не підключено, кнопка поверне помилку.

**Свідомо не перенесено з початкового технічного завдання на цю функцію** (щоб не роздувати проєкт компонентами й крихкими залежностями від внутрішніх API):
- **mDNS-браузинг** (`_shelly._tcp`, `_esphomelib._tcp`, `_http._tcp`) — прискорив би виявлення пристроїв, що самі анонсують сервіс, але додає ще один керований компонент (`espressif/mdns`, теж прибраний з ядра ESP-IDF v6.0.1) і ще один шлях збірки, який може зламатися. Ping+TCP:80+фінгерпринтинг уже покриває виявлення функціонально, просто трохи повільніше. *(Уточнення: для "назв" пристроїв (розділ вище) все ж таки додано мінімальний mDNS reverse-PTR запит вручну, без компонента `mdns` — це окремий, набагато простіший кейс: один UDP-пакет із зворотним запитом за вже відомою IP, а не повноцінний service browsing/анонсування.)*
- **Кешування знайденого за MAC у NVS з TTL** (щоб переживало перезавантаження роутера/зміну IP пристрою) — додає постійне сховище й TTL-логіку заради виграшу, який рідко того вартий (просто запускається новий скан). *(Уточнення: активне ARP-сканування як таке — саме навпаки — тепер реалізовано й навіть є основним механізмом виявлення, див. "Автопошук у мережі" → "Активний ARP-пробінг як основний, а не запасний, спосіб виявлення". Спершу (в попередній версії) було зроблено лише пасивне читання вже наявного ARP-кешу як фолбек до ping-скану; коли з'ясувалось, що можна активно тригерити ARP-резолюцію через звичайний UDP `sendto()` (без promiscuous-режиму й без lwIP-внутрішнього `etharp_request()`), цей підхід замінив ping на роль основного механізму повністю.)*
- **Нативний бінарний API ESPHome (порт 6053, protobuf)** — це окремий немаленький протокол; підтримується лише REST-евристика через вбудований `web_server` ESPHome (якщо в YAML пристрою він увімкнений і містить `switch`-сутність).
- **Sonoff DIY (порт 8081, `POST /zeroconf/info`)** та **виявлення Tuya на стоковій прошивці** (порти 6668/6666/6667) — не реалізовані; перший через обмежений час на реалізацію, другий за узгодженою від початку умовою проєкту (Tuya/Smart Life свідомо не підтримуються).
- **Пріоритезація сканування за OUI-префіксами Espressif** — не потрібна: фінгерпринтинг і так запускається лише проти вже відфільтрованого списку хостів з відкритим :80, а не проти всієї підмережі.
- **Окремі vtable-драйвери на кожну прошивку** (`driver_shelly.c`/`driver_tasmota.c`/`driver_esphome.c`) — не додавались: Shelly/Tasmota/ESPHome REST — це завжди "звичайний HTTP GET/POST за URL", що вже й так робить `driver_http.c`; фінгерпринтинг лише підбирає правильний URL-шаблон і підставляє його в ту саму, вже наявну, форму HTTP-розетки. У формі розетки "Shelly (Gen1)"/"Shelly (Gen2+/Gen3)"/"Tasmota" тепер є окремими пунктами випадаючого списку драйвера (див. розділ "Драйвери") — це суто UI-рівнева зручність (не питати повний URL, а лише IP), під капотом усі три лишаються `driver=http` + `http.family`, без окремого коду виконання.

## Надійність / вихід із зависань

Пристрій розрахований на тривалу безнаглядну роботу (24/7), тож окремо про те, що робить прошивка, якщо щось піде не так сама по собі, без втручання людини.

**Апаратний watchdog тепер справді перезавантажує, а не тільки пише в консоль.** У ESP-IDF за замовчуванням увімкнений Task Watchdog Timer (`CONFIG_ESP_TASK_WDT_EN`/`_INIT`, таймаут 5с, стежить за idle-задачами обох ядер) — але без `CONFIG_ESP_TASK_WDT_PANIC` спрацювання лише друкує попередження в консоль, а пристрій лишається працювати (точніше — висіти) як і був. Увімкнено `CONFIG_ESP_TASK_WDT_PANIC=y` (`sdkconfig.defaults`) — тепер спрацювання перезавантажує пристрій.

**Але сам по собі TWDT не бачить найімовірнішого класу зависання.** Він стежить лише за тим, чи виконується idle-задача — тобто ловить задачу, яка монополізувала ядро в нескінченному циклі. Якщо натомість дві задачі чекають одна на одну через м'ютекс (deadlock) — ЦП простоює нормально, idle-задача виконується, TWDT нічого не бачить, а система при цьому мертва. У проєкті послідовно дотримувались правила "мережевий виклик ніколи не під локом" саме для запобігання цьому — але це дисципліна коду, не запобіжник на рівні системи.

**`system_health.c`** — окрема фонова задача (`system_health_init()`, викликається з `app_main.c` після `web_server_start()`), яка додає три речі:

1. Підписує сама себе на TWDT і "годує" його кожні 2с (`HEALTH_LOOP_INTERVAL_MS`, з запасом під 5-секундний таймаут). Проста, коротка задача — якщо вона раптом перестане виконуватись вчасно (з будь-якої причини, включно з тим, що якась інша задача забрала собі ЦП), TWDT це також зловить.
2. Раз на 5 хвилин (`LOCK_PROBE_INTERVAL_MS`) пробує захопити внутрішні локи `plug_manager.c` та `net_scan.c` через нові `plug_manager_is_responsive()`/`net_scan_is_responsive()` — **обмеженим** очікуванням (2с, `LOCK_PROBE_TIMEOUT_MS`), на відміну від звичайних `portMAX_DELAY` в усіх інших функціях цих модулів. Саме це ловить deadlock, який TWDT не бачить: якщо лок не звільнився за 2с (обидва локи в нормі звільняються за одиниці мілісекунд), це вже сильний сигнал. Дві поспіль невдалі спроби (~5-10 хвилин підтвердженої проблеми) — і `system_health.c` свідомо викликає `esp_restart()`. Одна невдала спроба перезавантаження не викликає — щоб не рестартувати через одиничний збіг у плануванні задач на пристрої, для якого пріоритет — саме безперервна робота.
3. Якщо STA налаштована (є облікові дані — перевіряється через `wifi_manager_get_status()`'s `ssid_out`, порожній рядок означає "STA взагалі не налаштована", а не "не підключена"), не здалась у сенсі "неправильний пароль" (`wifi_manager_sta_config_error()`) і при цьому не підключена довше 15 хвилин (`WIFI_STUCK_RESTART_MS`) — попри те, що `wifi_manager.c` й так нескінченно ретраїть підключення сама (див. розділ "Wi-Fi") — перезавантажується як останній засіб. Деякі стани Wi-Fi-драйвера знімаються лише повним переініціалізуванням, не просто повторним `esp_wifi_connect()`. Перевірка налаштованості SSID важлива: без неї чисто AP-режим (без STA-облікових даних узагалі, штатний підтримуваний сценарій) перезавантажував би пристрій кожні 15 хвилин назавжди, бо `wifi_manager_is_connected()` там і так завжди `false`.

Додатково раз на 30 хвилин (`HEARTBEAT_INTERVAL_MS`) пишеться "heartbeat"-запис у журнал подій (`LOG_SRC_SYSTEM`, `uptime`/вільна internal SRAM/стан STA) — щоб наступне зависання (якщо станеться) лишило по собі хоч якийсь слід на флеш-памʼяті, а не повну відсутність даних для діагностики без живого підключення до серійного порту.

**Чого це свідомо не покриває:** апаратні причини (проблеми з живленням, USB-порт, що засинає вночі) — програмний watchdog тут безсилий; для цього залишається лише якісне живлення. Панік від справжнього стек-оверфлову вже ловиться окремо (`CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK`, див. `sdkconfig.defaults`) і так і так призводить до перезавантаження.

## Відомі спрощення / що варто допрацювати

- `status_url` в HTTP-драйвері поки не використовується для читання фактичного стану розетки (лише зберігається в конфігурації) — легко додати опитування статусу за потреби.
- NTP-клієнт "заряджається" один раз при старті через `esp_netif_sntp` — це нормально (SNTP сам періодично ресинхронізується у фоні), але явного "Синхронізувати зараз" в UI немає; за потреби легко додати кнопку, яка викликає `esp_netif_sntp_sync_wait`.
- Немає TLS/mTLS для HTTP чи MQTT (свідомо, за умовою задачі — лише прості HTTP/MQTT драйвери); за потреби `esp_http_client`/`esp-mqtt` підтримують `https://`/`mqtts://` без зміни архітектури.
- Автопошук — ping+TCP:80+фінгерпринтинг (Shelly/Tasmota/ESPHome), детальний список свідомо не реалізованого (mDNS, ARP/MAC-кеш, ESPHome native API, Sonoff DIY тощо) — див. розділ "Автопошук у мережі". Слухання MQTT discovery-топіків теж не реалізовано, але додається без зміни архітектури, якщо MQTT-брокер уже використовується для розеток.
- Вендорений `cJSON.c/h` — це не офіційна бібліотека DaveGamble/cJSON, а власна мінімальна реалізація з такою ж назвою функцій. Парсер толерантний до "сирого" JSON, який генерує сам пристрій, але не проходив повний conformance-тест (наприклад, юнікод-сурогатні пари `\uD8xx\uDCxx` не збираються в один кодпоінт — для ASCII-даних цього проєкту це не критично).
